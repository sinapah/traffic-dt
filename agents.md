We need to implement a discrete-event simulation of a smart traffic monitoring system consisting of three cameras, three edge nodes, a federated learning coordinator, and a system-level Digital Twin (DT). The purpose of the simulation is to evaluate whether a DT can improve resource orchestration and maintain system performance under dynamic workloads and telemetry outages.

The simulation should represent an accelerated timeline where **48 simulation minutes correspond to 48 operational hours**. Each simulation minute therefore represents one real-world hour. The workload should follow realistic traffic patterns over a two-day period. Traffic volume should vary throughout the day, with lower arrival rates during nighttime hours and significantly higher arrival rates during morning and evening rush-hour periods. The arrival rate should therefore be time-dependent rather than constant.

The system consists of three camera sources and three edge nodes. Each camera is permanently associated with a single edge node. Cameras continuously generate image arrivals based on a configurable frame rate schedule. The frame rates should vary throughout the simulation to emulate changing traffic conditions. For example, nighttime periods may generate low frame rates while rush-hour periods generate substantially higher frame rates. The simulation does not need to transmit actual images initially; image arrivals can be represented as events or workload units. If desired later, UA-DETRAC frames can be used as the underlying image source.

Each edge node should have a configurable processing capacity expressed as a service rate. The service rate represents how many frames the edge can process per unit time. The three edges should have different service rates to model heterogeneous hardware capabilities. For example, Edge 1 may process 25 frames per second, Edge 2 may process 35 frames per second, and Edge 3 may process 15 frames per second. These values should be configurable.

Each edge should maintain an input queue. Incoming frames generated by the associated camera are added to the queue. The edge continuously removes frames from the queue according to its service rate. Queue growth should therefore occur naturally whenever the arrival rate exceeds the service rate. The simulation should track queue length, waiting time, processing throughput, utilization, and dropped frames if a queue capacity limit is exceeded.

In addition to processing incoming frames, each edge participates in federated learning. Federated learning should operate on a separate periodic schedule. Every configurable interval (for example every five simulation minutes), each edge performs a local training cycle using data accumulated since the previous training interval. The simulation does not need to perform expensive deep learning initially. Training can be represented using a workload model where the duration and resource cost depend on parameters such as local epochs, batch size, and dataset size. These parameters should be configurable and modifiable during runtime.

A federated learning coordinator should aggregate updates from participating edges at the end of each federated learning round. The coordinator should maintain statistics such as round duration, participating clients, aggregation count, and convergence metrics. Initially, convergence can be represented by a simplified surrogate metric if a real object detection model is not yet integrated.

The Digital Twin should operate as a separate component that receives telemetry from all edge nodes. Telemetry should include queue length, utilization, processing rate, arrival rate, training duration, federated learning statistics, and any other relevant system metrics. The DT should maintain an internal state representation of both individual edge nodes and the overall system.

The DT should continuously record telemetry into a historical datastore. This historical information will later be used for prediction and telemetry synthesis. The DT should expose an interface that allows future replacement of prediction models without requiring architectural changes.

The DT should also support telemetry outages. During a telemetry outage, edge nodes continue operating normally, federated learning continues normally, and camera traffic continues normally. The only failure is that telemetry updates are no longer delivered to the DT. During these periods, the DT must continue estimating system state using previously observed telemetry. The architecture should support pluggable telemetry generation strategies. Initially, a simple historical prediction method can be implemented, but the design should include interfaces for future KDE-based and WGAN-based telemetry synthesis modules.

The DT should not directly modify the physical system. Instead, it should produce recommendations that are passed to an orchestration component. The orchestrator is responsible for applying policy changes to the edge nodes.

The orchestrator should support modifying operational parameters including local training epochs, local training frequency, frame sampling rates, federated learning aggregation intervals, and client participation schedules. These are the primary control variables available to the DT. The DT should use observed and predicted system conditions to recommend parameter changes that improve overall system performance.

The simulation should include multiple workload phases. During normal operation, telemetry is available and the DT receives real measurements. During outage periods, telemetry is unavailable and the DT must rely on estimated values. After telemetry is restored, the DT should compare estimated values against actual measurements and compute estimation error metrics.

The system should collect and store comprehensive evaluation metrics throughout the simulation. Metrics should include queue length, utilization, latency, throughput, dropped frames, federated learning round statistics, DT estimation accuracy, telemetry reconstruction error, and any orchestration actions applied during runtime.

The implementation should support comparing multiple configurations. At minimum, there should be a baseline configuration using fixed policies and a DT-driven configuration where orchestration decisions are generated dynamically. The simulation framework should allow direct comparison of queue growth, utilization, latency, federated learning behavior, and overall system stability between these approaches.

All metrics should be recorded over simulation time. Visualization support should include plots of queue length, utilization, latency, throughput, and DT estimation error versus simulation time. Telemetry outage periods should be clearly indicated on the plots. The resulting framework should make it possible to evaluate whether DT-driven orchestration improves system performance under changing workloads and telemetry disruptions.
